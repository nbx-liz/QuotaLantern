# ADR 台帳

QuotaLantern の設計上の決定を、1 件 1 ファイルで記録する。
Accepted の ADR は、このリポジトリで最も優先度の高い文書である（[CONTRIBUTING.md](../../CONTRIBUTING.md)）。

## ステータス

| ステータス | 意味 |
| --- | --- |
| Proposed | 案。実装の根拠にしてよいが、決定ではない。受入条件を満たすまで公開しない |
| Accepted | 決定済み。変更するには新しい ADR で置き換える |
| Rejected | 検討の結果、採用しない |
| Superseded | 後続の ADR に置き換えられた |

## 役割

| 役割 | 決めること | 担当 |
| --- | --- | --- |
| プロダクト責任者 | 範囲、表現、例外の承認 | @nbx-liz |
| 技術責任者 | 取得方式、データ契約、OS 対応 | @nbx-liz |
| セキュリティ担当 | 非保存、権限、通信のレビュー | @nbx-liz |

1 人で開発している間も、レビューの記録は役割ごとに分けて残す。
安全性は自己申告だけで合格にせず、試験の証跡を ADR か Issue に添付する。

## 延期中の検証（2026-10-22 のプロダクト責任者の判断）

G0 の検証は、当面この Linux 環境だけで行う。macOS / Windows の実機検証を行うまで、次の保証は確認されていない状態にある。

- ADR-0003 の UI-G1〜G5（QL-004）。WebView2 / WKWebView は実機でしか監査できない
- macOS / Windows での取得・非保存・通信の監査（SEC-01〜10）

この間、G0 を完了と宣言しない。対応表では macOS / Windows を「未検証」と記載する。

## 未決論点（ADR 未起票）

| ID | 論点 | 関係 | 決める時期 |
| --- | --- | --- | --- |
| Q-01 | stale の判定条件。暫定案は「受信間隔 3 分超」だが、Claude Code の Status line は応答のたびにしか更新されず、作業していない間はほぼ常に stale になる。「更新がない」と「提供元の障害」を区別する表示方針が要る。実機の材料（2026-10-22、Linux、実機試験 B）：Status line の 5 時間枠の残りが `/usage` より 2 ポイント多く、次の応答の後に一致した。Status line に渡る値は直前の応答の時点のもので、入力に提供元の時刻は無いため、受信した時刻だけでは鮮度を判断できない。`refreshInterval: 10` で数分間操作しなかった間にも、表示の数字は変わった（どの項目か、値がどこから来たかは未確認）。応答が無い間も新しい値が届くことがあるため、「応答のたびにしか更新されない」とは言い切れない | FR-03、ADR-0002 | Claude 取得試作（QL-002）の後 |
| Q-02 | 既存の Status line との共存。設定できるコマンドは 1 つで、既存の設定を上書きしない方針と両立する導入手順が要る | ADR-0005、FR-01 | QL-002 の後 |
| Q-03 | Codex の能動照会の間隔。暫定案は 60 秒、同時 1 件、タイムアウト 10 秒、失敗時は最大 15 分までの指数バックオフ。公式の推奨値ではない | ADR-0004 | Codex 取得試作（QL-003）の後 |
| Q-04 | 1 つの Status line 取得プロセスから、同一ユーザーの別プロセスによる偽装接続をどこまで排除できるか | ADR-0002、IPC | IPC 設計時 |
